# ADR-0004：短期 Worktree 任务与写前冲突门禁

- 状态：accepted
- 日期：2026-07-15

## 背景

PreVision 同时存在 Bug、新功能、UI 和工程工作。长期对话会积累过时上下文；不同 Worktree 又可能在摄影机、时间轴、项目数据或同一 UI 表面上做出互相矛盾的决定。主应用集中在单体 HTML，仅用文件重叠会把所有工作都判成冲突，也无法识别多个文件共同改变同一数据语义的情况。

## 决定

1. 固定 `00`–`05` 是长期讨论、分管和调度入口，**MUST NOT** 亲自实施代码、UI、测试、构建配置或其他项目文件变更。固定 `99` 永久只读。
2. 固定 `01`–`05` 只做需求讨论、澄清、只读分析、分类和验收口径，然后向固定 `00` 报告。即使用户明确说“开始做”“先做预览”或“继续”，它们也 **MUST NOT** 创建开发分支/Worktree、运行 `task:claim`、写入文件或提交实现。
3. 固定 `00` 只做 App/任务状态检查、冲突识别、依赖和集成顺序、临时工创建与派发、提交接收和机械集成、最终回归、稳定预览，以及获得用户授权后的固定 App 交付。`00` **MUST NOT** 在长期任务中编写业务或治理实现；集成冲突只能在不改变已验收语义的前提下解决。
4. 所有实际代码、UI、测试实现、构建实现或其他项目文件写入都 **MUST** 由 `00` 从最新集成基线，通过 Codex 项目 Worktree 新建并委派给用户侧栏可见的独立短期临时工任务。“侧栏可见”是指该任务作为独立任务出现在用户的 Codex 项目侧栏，可由用户打开、观察并在结束后归档；每个可独立验收的结果使用自己的对话、Worktree、分支、验收单和 write claim。仓库测试只验证规范及文件证据的一致性，不冒充 Codex App 内部状态检测。
5. 内部 collaboration/sub-agent 只能用于只读审计、代码审查、测试复核和调研；**MUST NOT** 修改项目文件、创建实现提交或持有 write claim。需要写入的发现必须交回 `00`，由其创建用户侧栏可见任务。
6. 不预建空任务。`qa/task-scope-taxonomy.json` 提供按需路由模板和统一范围名称；固定入口不因名称含“开发”或“发布”而获得写权限。
7. 临时工在首次写入前声明模块、UI 表面、数据区域和文件。声明保存在 Git common dir，使所有 Worktree 可见，但不进入提交；固定 `00`–`05` 自身不得登记 write claim。
8. 模块、UI 表面或数据区域重叠为硬冲突；只有文件重叠为软冲突。硬冲突在写入前阻止，软冲突必须由 `00` 指定集成顺序。
9. 单体架构阶段同时最多两个临时工写任务。只读审查不占名额，但不得修改文件。
10. 临时工完成后只向 `00` 交接提交和证据，不自行更新固定 App。任务完成或取消后保持 claim；`00` 确认集成成功或取消后 release，并归档对应侧栏任务。

## 替代方案

- 长期保留每个细分方向的空任务：会保留旧基线和多余上下文，拒绝。
- 只依赖 Git 文件冲突：无法识别逻辑和数据冲突，在单体 HTML 中误报过多，拒绝。
- 完全串行：安全但失去可并行的独立工作，拒绝。
- 允许任意数量写任务：当前单体架构整合成本过高，拒绝。

## 后果

- 用户提出新请求时会先得到冲突说明，再决定等待、拆分或改变顺序。
- 两项逻辑独立但同改单体 HTML 的工作仍可并行；最终集成成本由总协调显式承担。
- 固定 `00`–`05` 只保留长期讨论与决策上下文，实际开发上下文全部随短期临时工归档，更易复现也不会污染固定入口。
- 用户在任何固定入口发出开工指令时都会多一次“提交 `00` → 创建临时工”的显式路由；这是保证职责边界的必要成本。
- 声明准确性成为开发责任，验收单和评审必须核对声明与真实 diff。

## 验证方式

- `npm run test:coordination`
- `npm run test:foundation`
- 自动断言确认 `AGENTS.md`、开发流程和本 ADR 同时保留固定 `00`–`05` 的 **MUST NOT** 规则、临时工 **MUST** 写入规则，以及 `00` 集成/release 边界。
- 人工在两个 Worktree 声明独立范围，再声明重叠范围并确认硬冲突信息。

## 撤销条件

当主应用拆分为可独立构建的模块、自动语义依赖图足以替代人工范围，或团队迁移到具备同等写前门禁的外部任务系统时，可新建 ADR 替代本决定。
